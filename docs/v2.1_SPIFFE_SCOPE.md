# Kryptkeeper v2.1 — SPIFFE/SVID Workload Identity (Scope)

**Date:** 2026-06-18
**Plan reference:** `docs/archive/GO_FORWARD_PLAN.md` v2.0 row (split out as its own release)
**Status:** SHIPPED — v2.1.0 (tagged; see CHANGELOG.md). This doc is the original scoping record; per-item statuses below are historical. _(Re-statused 2026-07-15, design review G-7.)_

## 1. The thesis

Workloads (services, pods, functions) need cryptographic identity, not
long-lived secrets. SPIFFE is the standard: each workload gets a short-lived
**SVID** (an X.509 cert whose SAN is a `spiffe://trust-domain/workload` URI) and
a **trust bundle** to verify peers. Kryptkeeper already has a CA, short-lived
profiles, and PQC issuance — v2.1 adds the SPIFFE shape so it can be a SPIFFE
server / `spiffe-helper`-compatible issuer.

## 2. What already exists (code-verified 2026-06-18)

- **CA engine + issuance** (`internal/ca/engine.go`) — but issuance sets
  `DNSNames` only; **there is no URI SAN support.** A SPIFFE ID is a URI SAN, so
  this is the foundational gap (and URI SANs are generally useful beyond SPIFFE).
- **Short-lived cert profiles** (templates) — SVIDs are short-lived; reuse.
- **Trust chain / CA bundle** plumbing exists (chains, CRL/OCSP).
- **Protocol-server pattern** — acme/est/scep/cmp/xcep/wstep each mount under
  the Hub; a SPIFFE endpoint follows the same shape.
- No gRPC anywhere yet; no SPIFFE/SVID/trust-domain code.

## 3. Scope decision — issuer + bundle now; gRPC Workload API + attestation later

The full SPIFFE Workload API is a **gRPC** streaming service with node/workload
**attestation** — a large effort and a new gRPC dependency. To deliver usable
workload identity without that, **v2.1 = URI-SAN issuance + an SVID mint endpoint
+ the trust-bundle endpoint**, auth-gated. The gRPC Workload API and real
attestation are a follow-up (**v2.1.x**), noted but not built here.

- **v2.1.x — SPIFFE Workload API (gRPC)**: `FetchX509SVID` streaming +
  node/workload attestation, for `go-spiffe` / `spiffe-helper` clients.

## 4. Deliverables

### A. URI SAN support (foundational)

- `CertificateIssueRequest` gains `URISANs []string`; the CA engine template
  sets `template.URIs` (parsed `*url.URL`), and falls back to the CSR's URIs.
- Surface URI SANs in `CertificateItem` (display + the cert detail panel).
- Validation: well-formed URIs; for SPIFFE, scheme must be `spiffe`.

### B. Trust domain + SVID minting

- Config: `SPIFFE_TRUST_DOMAIN` (e.g. `example.org`) and which CA signs SVIDs.
- `POST /api/v1/spiffe/svid` — mint a short-lived SVID for a
  `spiffe://<trust-domain>/<path>` ID. Validates the ID's trust domain matches
  config; issues via the CA engine with the SPIFFE ID as the URI SAN, a
  short TTL (reuse short-lived profile), and key usage for client+server auth.
  Auth-gated (a principal/agent authorized to request that workload's identity).
- Returns the SVID cert + key + the signing chain.

### C. Trust bundle

- `GET /api/v1/spiffe/bundle` — the trust domain's CA bundle (PEM, and the
  SPIFFE JWKS-style trust-bundle JSON) so peers/clients can verify SVIDs.

### D. Dashboard

- A SPIFFE panel: trust domain, the SVID-signing CA, recently-issued SVIDs
  (filter the inventory by `spiffe://` URI SAN), and a "mint SVID" form for
  testing.

## 5. Waves

| Wave | Content | Notes |

| **W1** | URI SAN support (engine + issuance + CertificateItem + detail UI) | Foundational; useful on its own |

## 6. Risks

- **URI SAN correctness**: SPIFFE IDs have strict rules (scheme `spiffe`, no
  port, no query/fragment, host = trust domain). Validate strictly.
- **SVID hygiene**: SVIDs are short-lived and often have an empty Subject (the
  identity is the URI SAN). Ensure the profile allows that.
- **Not the full Workload API**: be explicit this is mint+bundle, not the gRPC
  attestation flow — manage expectations vs `go-spiffe` clients.
- **Trust-domain mismatch**: reject SVID requests whose ID trust domain ≠ config.

## 7. Decisions (locked 2026-06-18)

1. **v2.1 = REST SVID mint + trust bundle.** The gRPC SPIFFE Workload API and
   node/workload attestation are deferred to **v2.1.x**.
2. **SVID signing CA: config-selected existing CA** (`SPIFFE_SIGNING_CA_ID`);
   docs recommend a dedicated SPIFFE intermediate as best practice.
3. **SVID TTL: 1 hour default**, configurable (`SPIFFE_SVID_TTL`).
4. **Mint auth: admin/operator only** for v2.1 (finer-grained later).
