# W26-19 - hub-rooted workload identities (SPIFFE SVIDs) on kind

Proves on a real kind cluster (podman provider) that two pods obtain SVIDs from
the hub's SPIFFE Workload API for a registered selector and complete mutual TLS
verified to the hub root. Operator guide: `docs/guides/istio-hub-ca.md`.
Results: `docs/release/LIVE_RESULTS_FG2_MESH_v0.14.md`.

## Run

```
bash tests/live/istio-mtls/run.sh
```

Prerequisites: `kind kubectl podman openssl curl python3 go`; a running podman
machine (shared with CI: run serially); network to pull `busybox:1.36`, the
Go and distroless base images, and the go-spiffe modules for `go vet`.

| Env | Default | Meaning |
|---|---|---|
| `CLUSTER` | `kk-uat-mesh` | kind cluster name |
| `LPORT` | `18199` | local port of `kubectl port-forward` to the hub Pod |
| `KEEP_CLUSTER` | `0` | `1` leaves the cluster and temp dir |

Ends with `ALL STEPS PASSED`, `MEASURE key=value` lines (paste into the results
doc) and a separate `PATH_I: ...` line.

## What it proves (Path S, mandatory)

1. Hub Pod (sqlite, bootstrap auth, plain HTTP) with `SPIFFE_TRUST_DOMAIN=kk-uat.example`,
   `SPIFFE_SIGNING_CA_ID` (second round, after the root CA exists) and
   `SPIFFE_WORKLOAD_SOCKET=/run/kk-spiffe/api.sock` on a `hostPath`.
2. `POST /api/v1/spiffe/workload-selectors`: UID 2001 -> `.../sa/server`, UID 2002 -> `.../sa/client`.
3. `svid-server` (UID 2001) and `svid-client` (UID 2002) fetch SVIDs over the socket
   and run go-spiffe mTLS authorizing each other by SPIFFE ID: `PEER <id>` and
   `CHAIN_OK` on both sides.
4. Independent check: the client's leaf is dumped and `openssl verify -CAfile`
   against `GET /api/v1/spiffe/bundle` succeeds; the Workload API bundle root
   equals the hub root (sha256).
5. UID 2003 (unregistered) gets gRPC `PermissionDenied`, no SVID (acceptance 2, negative).
6. Audit holds `spiffe.selector_bind` rows (and `spiffe.workload_attest`, recorded only).

## Path I (Istio `cacerts`): not attempted

The spec makes it optional and best-effort: it needs a CA-capable template with an
exportable intermediate key and `istioctl`, neither verified on the lab host. The
harness prints `PATH_I: NOT_ATTEMPTED`; the guide documents Path S only.

## Notes and traps

- The Workload API is a Unix socket: hub and workloads share the single node's
  filesystem via `hostPath /run/kk-spiffe`. It is not exposed over TCP.
- The hub creates the socket mode 0755 and connect(2) needs write permission, so
  the hub Pod has a root sidecar that chmods it 0666 (a finding to confirm on
  the first run; the hub does not chmod its socket).
- The svidclient image builds with `golang:1.26-alpine` (not 1.23 as the spec
  says): go-spiffe v2.8.1 requires Go 1.24+.
- If container UIDs are remapped, the hub sees another number; a denied
  attestation message names the UID it saw (`uid N is not a registered workload`)
  and the script surfaces it. Do not guess.
- `FetchX509SVID` is the only method implemented. go-spiffe's `X509Source` is
  expected to need only that; if the run shows `FetchX509Bundles` being
  demanded, record it as a finding and fall back to the raw client.
- No key is committed: the SVID key is generated by the hub per request and
  never leaves the pod; secrets are random per run.
