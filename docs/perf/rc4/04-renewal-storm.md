# RC4 perf: renewal-storm drain (W30-22)

`tests/perf/storm.sh` makes N certificates due at once, drains them with simulated agents through
`POST /api/v1/certificates/{fingerprint}/renew`, and reports the minutes between the first and the last
`certificate.renew` success audit event (`GET /api/v1/audit?action=certificate.renew&outcome=success`,
`order=asc|desc&limit=1`). Postgres 16, `APP_AUDIT_PROVIDER=db`.

```bash
bash tests/perf/storm.sh --certs 50000 --agents 16 --rate 0 --out storm-out    # writes storm-out/storm.json
KK_PERF_RESULTS=$PWD/storm-out/storm.json go test ./tests/perf/... -count=1 -v
```

## Method

1. `perf_up 1000` (from `bench.sh`): real hub, 1,000 certificates (500 issued through the API, the rest cloned).
2. Insert `--certs` more rows cloned from renewable rows (`renewal_status='active'`, no successor, not
   revoked) with `valid_until = now() + 10 days`; assert the due count equals `--certs`.
3. `--agents` workers via `xargs -P`. Each worker generates a fresh P-256 CSR with `openssl`, then POSTs it
   (`{"csr_pem": ...}`) to the renew endpoint with a bearer token. The token is minted once and re-minted
   every 8 minutes. `--rate R` adds a per-worker pause of `AGENTS/R` seconds (R requests/s overall); `0` is unlimited.
4. Drain is complete when the success `Total` minus the baseline equals `--certs`; no progress for 10 minutes
   (`STORM_STALL_SECS`) ends the run with the partial count.
5. `storm.json` holds certs, agents, rate, success, failures, `storm_drain_minutes`, first/last event, HTTP
   code histogram and peak hub RSS. The script exits 0; the Go test (`TestStormMeetsBar`) judges it: zero
   failures, `storm_drain_minutes` under the bar, and no regression against a non-null baseline.

Audit timestamps have one-second resolution, so `storm_drain_minutes` is accurate to about 0.03 minutes.

## Budgets

| Key | Run | Bar | Baseline |
|---|---|---|---|
| `storm_drain_minutes` | 50,000 certs | < 60 min | null |
| `storm_drain_minutes_5k` | 5,000 certs (nightly) | < 6 min | null |

Baselines stay null: no 50,000-cert run has been made, and a baseline is only recorded from a run that
passes every bar. The nightly `perf-regression` job runs the 5,000-cert storm; the 50,000-cert run is the
`renewal-storm-full` job (workflow_dispatch with `storm_full=true`) until a measured 50k drain takes under
20 minutes.

## Results

Environment: Apple M4 Max, macOS 27.0.1, PostgreSQL 16.15 (`docker.io/library/postgres:16`, the lane is
offline for registry pulls), client and server on one machine, commit `e1702631` plus this change, 2026-10-16.

| Run | Certs | Agents | Rate | Drain (min) | Success | Failures | HTTP | Peak RSS (MiB) | Status |
|---|---:|---:|---|---:|---:|---:|---|---:|---|
| Smoke | 40 | 4 | unlimited | 0.07 | 40 | 0 | 201 x 40 | 125.8 | measured, no bar applies |
| Scaled nightly | 5,000 | 16 | unlimited | 1.37 | 5,000 | 0 | 201 x 5000 | 231.8 | measured, PASS (< 6) |
| Full | 50,000 | 16 | unlimited | | | | | | PENDING-RUN |
| Full, rate-limited | 50,000 | 16 | 20/s | | | | | | PENDING-RUN |

The 5,000-cert run drained at about 61 renewals/s (5,000 in 82 s between first and last event). That is
not a 50k result: nothing here shows the rate holds as the audit and certificates tables grow ten times.

### PENDING-RUN commands

```bash
# Gated run, bar 60 min (use PG_IMAGE=docker.io/library/postgres:16 where :16.15 cannot be pulled)
bash tests/perf/storm.sh --certs 50000 --agents 16 --rate 0 --out storm-out-50k
KK_PERF_RESULTS=$PWD/storm-out-50k/storm.json go test ./tests/perf/... -count=1 -v

# Upstream-limited run (Let's Encrypt-style 20 req/s ceiling; 50000/20 is at least 41.7 min). Reported, not gated.
bash tests/perf/storm.sh --certs 50000 --agents 16 --rate 20 --out storm-out-50k-rate20
```

The rate-limited run writes the same `storm.json` but is reported only, not gated: it measures capacity
under an upstream ceiling, so do not point `KK_PERF_RESULTS` at it.

## What this does not measure

- The hub scheduler's serial renewal loop. The scheduler's own auto-renew emits `certificate.renew_execute`
  (`renewal_scheduler.go`) and needs a real SSH target per certificate, so a 50,000-cert simulation cannot
  drive it. This run drives `certificate.renew` through the API with N parallel agents: CA signing, DB
  writes, audit append.
- SSH install, connector admission control or upstream throttling. UC-M11 records throttling as not built;
  `--rate` is a client-side cap that simulates an upstream CA limit.
- Agent-side key generation cost on real hosts; CSRs are generated by the load driver on the same machine.

## Verdict

Scaled nightly (5,000 certs): PASS: drained in 1.37 min (<= 6).
Full (50,000 certs): PENDING-RUN, no verdict. An unmeasured extrapolation of the 5k rate is about 14 minutes,
and it is not evidence.
