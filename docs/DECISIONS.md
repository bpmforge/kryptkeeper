| D-122 | **Key dual control is on by default (2026-10-09, owner decision after the security audit).** `KRYPTKEEPER_KEY_DUAL_CONTROL` unset or anything other than `false` means ON; only an explicit `false` (case-insensitive) disables it, and the hub then logs a startup WARNING. Every route that lets private key material leave the hub is covered, not only `POST /keys/{id}/export`: `/admin/backup` (`key_backup`), `/keys/escrow` (`key_escrow`) and its recovery (`key_escrow_recover`), `/keys/leaf-escrow` (`key_leaf_escrow`) and its recovery (`key_leaf_escrow_recover`), and `/keys/byok/export` (`key_byok_export`) all answer 202 with an `action_id`, a DIFFERENT human approves it in the pending-action queue, and the proposer redeems a single-use grant (10-minute TTL) by repeating the request with `approved_action_id`; recovery and BYOK grants are bound to the digest of the bundle the approver saw. With the guard on and the queue unreachable the routes fail closed (503). **Separation of duties follows the human, not the credential:** API keys record `created_by` (the minter's canonical human; a key minted by a key resolves to the first human), so a key an admin mints under any `principal_id` cannot approve that admin's proposals (nor can the admin approve proposals made with that key); the bootstrap token never approves or rejects (setup/break-glass credential); `mcp-agent` still never approves. **Approvals execute once:** the approve path wins a compare-and-set (`pending` to `executing`) BEFORE running the executor, so racing approvals run the action once and losers get 409.
