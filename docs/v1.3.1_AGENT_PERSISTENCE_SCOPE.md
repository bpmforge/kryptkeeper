# Kryptkeeper v1.3.1 — DB-backed Agent Store (Scope)

**Date:** 2026-06-17
**Status:** SHIPPED — v1.3.1 (tagged; see CHANGELOG.md). _(Status added 2026-07-15, design review G-7.)_
**Branch:** `feat/v1.3.1-agent-persistence`
**Why:** v1.3.0 shipped Renewal Autopilot, but the agent registry is in-memory —
a Hub restart wipes agent registrations, tasks, endpoints, and results. Agents
would have to re-register and the SLO/audit history would reset. This makes the
"renew forever" promise untrustworthy in production. Persistence is the top
hardening item.

## Goal

Agent state survives a Hub restart, with no behavior change when the DB is
unavailable (fall back to in-memory, as the other providers do).

## Design

### Interface + two implementations

`AgentStore` becomes an interface (it is a concrete struct today). Methods are
unexported (only `internal/bootstrap` implements it):

```
register, heartbeat, submitInventory, getTasks, list,
endpointsFor, submitRenewalResult, resultsFor,
allResults, endpointCount, agentCounts
```

- `memAgentStore` — the current implementation, renamed. `NewAgentStore()`
  returns it (keeps every existing unit test on the in-memory path, untouched).
- `dbAgentStore` — new SQLite/Postgres implementation, built via the existing
  `newDBProviderState` helper (same pattern as `approval_store.go`).
- `NewAgentStoreFromEnv()` — returns the DB store when `KRYPTKEEPER_DB_MODE` is
  set (falls back to memory on open error); wired into `RegisterHandlers`.

### Shared assignment logic (no duplication)

The cert→endpoint matching in `assignTasksLocked` is extracted into a pure
function:

```go
func matchRenewalTasks(
    inventory []AgentDiscoveredCert, endpoints []AgentEndpoint,
    existingTasks []AgentRenewalTask, results []AgentRenewalResult,
    thresholdDays int, now time.Time, newID func() string,
) []AgentRenewalTask // tasks to ADD
```

Both backends call it — the memory store on its in-memory slices, the DB store
on rows loaded inside the submit transaction. Identical behavior, one source.

### Schema — migration `000015_agent_store`

```sql
CREATE TABLE agents (
    id TEXT PRIMARY KEY, name TEXT NOT NULL, type TEXT NOT NULL,
    token TEXT NOT NULL, registered_at TEXT NOT NULL,
    last_seen TEXT, inventory_count INTEGER NOT NULL DEFAULT 0
);
CREATE TABLE agent_inventory (
    agent_id TEXT NOT NULL, fingerprint TEXT NOT NULL, subject TEXT,
    issuer TEXT, not_before TEXT, not_after TEXT, source TEXT,
    auto_renewable INTEGER NOT NULL DEFAULT 0
);
CREATE TABLE agent_endpoints (
    agent_id TEXT NOT NULL, server_type TEXT, cert_path TEXT,
    key_path TEXT, server_name TEXT, listen_port INTEGER, config_path TEXT
);
CREATE TABLE agent_tasks (
    task_id TEXT PRIMARY KEY, agent_id TEXT NOT NULL, fingerprint TEXT,
    subject TEXT, action TEXT, ca_url TEXT, not_after TEXT,
    server_type TEXT, cert_path TEXT, key_path TEXT,
    reload_method TEXT, verify_host_port TEXT
);
CREATE TABLE agent_results (
    id TEXT PRIMARY KEY, agent_id TEXT NOT NULL, task_id TEXT,
    fingerprint TEXT, outcome TEXT, served_fingerprint TEXT,
    rolled_back INTEGER NOT NULL DEFAULT 0, detail TEXT, reported_at TEXT NOT NULL
);
```

`inventory` and `endpoints` are replace-all per submit (delete agent's rows,
insert current). `agent_results` is capped to the most recent N per agent
(matching the in-memory `maxAgentResults`).

### Transactions

`submitInventory` runs in one transaction: replace inventory + endpoints, load
tasks + results, compute new tasks via `matchRenewalTasks`, insert them.
`submitRenewalResult` runs in one transaction: insert result, delete the
completed task, trim history.

## Out of scope

- Migrating existing in-memory agents (there are none persisted by definition).
- Token hashing at rest (tokens are random per-agent; a follow-up could hash
  them — noted, not done here to keep the wave focused).

## Test plan

- `dbAgentStore` against SQLite (temp file): register/auth, inventory+endpoints
  round-trip, task assignment (mirror the 7 memory assignment scenarios),
  result reporting + task clearing, SLO aggregation methods.
- Existing in-memory tests stay green unchanged (they use `NewAgentStore()`).
