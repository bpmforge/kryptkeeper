Close the gap between shipped backend capability and UI/operability. v1.1.0
already delivered the Approvals UI and the two real risk signals
(`OUTLIVES_NIST_SUNSET`, `SAN_SPRAWL`). The remaining v1.2 items:

3. **Renewal-scheduler status panel** (operability).
4. **SIEM settings page** (config is API-only).
5. **SSH-key + code-signing inventory pages** (API-only).

## Latent bug found during design

`RenewalScheduler` (`internal/bootstrap/renewal_scheduler.go`) is fully built
but **never started** — there is no `.Start()` call anywhere in `cmd/` or
`internal/`. It is dead code. The v1.2 scheduler status panel is meaningless
unless the scheduler actually runs, so item 3 includes wiring it into server
startup.

## 1. Posture snapshots (foundation)

### Data model — migration `000014_posture_snapshots`

```sql
CREATE TABLE IF NOT EXISTS posture_snapshots (
    id                  TEXT PRIMARY KEY,
    captured_at         TEXT NOT NULL,   -- RFC3339 UTC
    total_certs         INTEGER NOT NULL,
    pqc_score_percent   INTEGER NOT NULL,
    automation_percent  INTEGER NOT NULL,
    risk_critical       INTEGER NOT NULL,
    risk_high           INTEGER NOT NULL,
    risk_medium         INTEGER NOT NULL,
    risk_low            INTEGER NOT NULL,
    expired             INTEGER NOT NULL,
    expiring_47d        INTEGER NOT NULL,
    report_json         TEXT NOT NULL    -- full CryptoPostureReport for drill-down
);
CREATE INDEX IF NOT EXISTS idx_posture_snapshots_captured ON posture_snapshots(captured_at);
```

`report_json` stores the full `CryptoPostureReport` so we never lose fidelity;
the flat columns make trend queries cheap. Columns use `TEXT`/`INTEGER` so the
same DDL runs on SQLite and Postgres.

### Store — `posture_snapshot_store.go`

Mirrors `approval_store.go`: `PostureSnapshotStore` interface with sqlite +
postgres implementations, built via `newDBProviderState`. Adds `EnsureSchema`
(idempotent `CREATE TABLE IF NOT EXISTS`) called at construction so the daily
job never crashes on a fresh DB even if migrations weren't applied.

```go
type PostureSnapshot struct {
    ID, CapturedAt string
    TotalCerts, PQCScorePercent, AutomationPercent int
    RiskCritical, RiskHigh, RiskMedium, RiskLow int
    Expired, Expiring47d int
    Report CryptoPostureReport
}

type PostureSnapshotStore interface {
    EnsureSchema(ctx context.Context) error
    Save(ctx context.Context, s PostureSnapshot) error
    List(ctx context.Context, since string, limit int) ([]PostureSnapshot, error)
    Latest(ctx context.Context) (PostureSnapshot, bool, error)
}
```

### Daily job — `posture_scheduler.go`

Same ticker shape as `RenewalScheduler` (run-once-at-start + 24h ticker,
`Start()`/`Stop()`, env `POSTURE_SNAPSHOT_HOURS` default 24). Each tick:
list certs → `computeCryptoPosture` → flatten → `Save`. De-dupes within the
same UTC day (one snapshot/day) so restarts don't spam rows.

### API — `GET /api/v1/reports/crypto-posture/trend`

Query params: `since` (RFC3339, default 90d ago), `limit` (default 365).
Returns `{ "data": { "snapshots": [...] } }`. Auth same as other reports.

## Code-signing & SSH inventories (item 5 in plan)

Design-time finding: `internal/sshkeys` and `internal/codesign` are full library
packages but **completely unwired** — no HTTP routes, and nothing populates
them (the in-memory inventories are never filled; no discovery/agent path feeds
SSH keys). The go-forward plan's "API-only" label was optimistic.

- **Code-signing — shipped.** Derived live from the existing certificate
  inventory: certs whose extended key usage includes `codeSigning`. Real data,
  no new population subsystem. `GET /api/v1/inventory/code-signing` + a Code
  Signing page under Operations.
- **SSH keys — DEFERRED.** No data source exists. A page would be permanently
  empty until SSH discovery is built (scan `known_hosts`/`authorized_keys` via
  agent or host scan), which is a sizable effort well beyond v1.2's visibility
  scope. Tracked as deferred debt; revisit when designing a discovery source
  (candidate for v1.3 Renewal Autopilot, which already touches host agents).
