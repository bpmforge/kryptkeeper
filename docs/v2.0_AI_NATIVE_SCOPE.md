# Kryptkeeper v2.0 — AI-Native PKI Operations (Scope)

**Date:** 2026-06-18
**Plan reference:** `docs/archive/GO_FORWARD_PLAN.md` §4 Moat 3
**Status:** SHIPPED — v2.0.0 (tagged; see CHANGELOG.md). This doc is the original scoping record; per-item statuses below are historical. _(Re-statused 2026-07-15, design review G-7.)_

## 1. The thesis

> PKI ops is conversational by nature ("what expires this month?", "rotate
> everything that CA signed") and dangerous enough to need guardrails. We have
> the guardrail already: the **approval workflow**. Agentic ops with
> human-in-the-loop approval built into the PKI itself does not exist anywhere.

v2.0's centerpiece is an **MCP server**: an AI assistant can read the full PKI
posture and *propose* changes, but **every write routes through the approval
queue** — the AI proposes, a human approves, the audit log records both.

Killer demos:
- *"Show me every cert that fails PCI 4.2.1.1 and draft the remediation plan."*
- *"CA-7 is compromised — stage bulk revoke + re-issue for everything it signed,
  queued for my approval."*

## 2. Scope decision — MCP is v2.0; SPIFFE and multi-tenancy are deferred

The go-forward plan groups MCP + SPIFFE/SVID + multi-tenancy under v2.0. They are
three **independent, large** efforts. To ship the actual category-creating moat
without a mega-release, **v2.0 = the MCP server.** SPIFFE/SVID (workload
identity) and multi-tenancy (policy folders) get their own scopes:

- **v2.1 — SPIFFE/SVID issuance**: a SPIFFE Workload API endpoint issuing SVIDs;
  independent of MCP; sizable (trust domains, attestation).
- **v2.2 — Multi-tenancy**: policy folders / tenant isolation across CAs,
  templates, RBAC; cross-cutting and the largest. Best done deliberately, late.

This doc scopes **the MCP server**. The other two are noted, not detailed.

## 3. What already exists (code-verified 2026-06-18)

- **The guardrail**: an approval workflow (`ApprovalStore`, role-based
  `handleApprove`, template `approval_roles`). **But it's issuance-only** —
  `ApprovalRequest` models a CSR + template + issued fingerprint, not
  revoke/rotate/renew. v2.0 must generalize it (see §4 B).
- **94 REST endpoints** — the capability surface the MCP tools wrap.
- **Auth + RBAC**: `AUTH_MODE` (bootstrap/jwt/oidc), principals with roles
  (pki-admin, pki-auditor) and scopes; `AuthenticatePrincipal`. MCP auth reuses
  this — a tool call carries a principal, and the REST layer enforces RBAC.
- **Audit**: every action already audited — AI-proposed and human-approved
  steps drop in naturally.

No MCP code, no Go MCP dependency yet.

## 4. Deliverables

### A. MCP server — read tools (the safe, immediately-demoable half)

A new binary `cmd/kryptkeeper-mcp` that is a **thin protocol adapter**: each MCP
tool call maps to a Hub REST call carrying the caller's token, so existing auth,
RBAC, and audit apply unchanged. Read tools:

- `list_certificates` (filters), `get_certificate`, `search`
- `crypto_posture`, `pqc_countdown`, `renewal_slo`, `compliance_evidence`
- `list_cas`, `ca_health`, `audit_query`

Read-only is safe to ship first and demos instantly ("what expires this month?").

### B. Generalized approval queue (the prerequisite for safe writes)

The issuance-only `ApprovalRequest` can't represent "revoke these 40 certs."
Add an **action-approval** model (new table `pending_actions`, migration):

```
PendingAction {
  id, action_type (issue|renew|revoke|rotate|bulk_revoke),
  params_json,                 // the proposed change
  proposed_by,                 // "mcp:agent" or a principal
  rationale,                   // the AI's stated reason
  status (pending|approved|rejected|executed|failed),
  approved_by, decided_at, result_json, created_at
}
```

Approve → the Hub executes the action via the existing providers and records the
result; reject → no-op. RBAC: only approver roles can approve (reuse
`isApproverForTemplate`-style checks). This is independently useful (a generic
"change request" queue) beyond MCP.

### C. MCP server — write tools (approval-gated)

Write tools **never mutate directly** — they create a `PendingAction` and return
its id:

- `propose_issue`, `propose_renew`, `propose_revoke`, `propose_rotate`,
  `propose_bulk_revoke` (e.g. "everything CA-7 signed")
- `list_pending_actions`, `get_pending_action` (so the AI can report status)

The human approves in the dashboard (or via an approver tool gated to
approver-role principals). Every step is audited: proposed-by-AI + approved-by-human.

### D. Dashboard — pending actions queue

A "Pending Actions" page: AI-proposed changes with rationale, diff/summary, and
approve/reject. Extends the existing Approvals UI pattern to the generalized
queue.

### E. Safety & guardrails

- **Writes are proposals, full stop** — the MCP server has no direct-mutation
  path; it can only enqueue. Enforced structurally, not by policy.
- **Scoped tokens**: the MCP server authenticates with a principal whose role
  can propose but **cannot self-approve** (proposer ≠ approver).
- **Rate/size caps**: bulk proposals capped (reuse the bulk-op 500/200 caps);
  log truncation.
- **Audit everything**: tool call → proposal → approval → execution, linked by
  action id.

## 5. Waves

| Wave | Content | Notes |
|------|---------|-------|
| **W1** | MCP server skeleton (binary, transport, auth bridge) + read tools | Safe, immediately demoable; no mutation path |
| **W2** | Generalized `pending_actions` queue (model, execute-on-approve, RBAC) + dashboard Pending Actions page | The guardrail; useful on its own |
| **W3** | MCP write tools (propose_*) on top of W2 + the CA-compromise demo script | The moat; structurally proposal-only |

## 6. Decisions (locked 2026-06-18)

1. **MCP transport: stdio first** (Claude Desktop / local AI clients; simplest,
   demoable). Streamable HTTP is a follow-up (v2.0.1).
2. **MCP library: `github.com/mark3labs/mcp-go`** (mature, pure Go) unless the
   API check at W1 favors the official SDK. Verify before coding (pre-code rule).
3. **Architecture: separate binary** (`cmd/kryptkeeper-mcp`) calling the Hub
   REST API — max reuse of auth/RBAC/audit/approval; the adapter holds no
   mutation logic.
4. **v2.0 = MCP server only.** SPIFFE/SVID → v2.1, multi-tenancy → v2.2 (separate
   scopes).

## 7. Risks

- **MCP spec churn**: the protocol is young; pin the library version and isolate
  the adapter so a spec bump touches one layer.
- **Over-trust**: the whole value is that the AI *can't* act alone — keep the
  proposal-only invariant inviolable (no "auto-approve" flag, ever).
- **REST coupling**: a thin adapter must handle Hub auth/token plumbing; design
  the token model up front (service principal for the MCP server).
