## 1. The thesis

One Kryptkeeper instance, many isolated tenants. A tenant sees and uses only
**its own** CAs, templates, certificates, reports, and approvals; a super-admin
operates across all. This unlocks MSP / platform-team / business-unit
deployments without standing up an instance per tenant.

## 2. Honesty up front — this is the largest, riskiest release

Multi-tenancy is **cross-cutting and security-critical**: it touches auth, every
store (CA, template, certificate, approval, pending-action, schedules, waves),
and every list/mutation handler. A single missed filter is a **cross-tenant data
leak**. It must be done deliberately, in phases, with isolation tests that
actively try to cross the boundary. The go-forward plan put it last for this
reason.

## 3. What already exists (code-verified 2026-06-18)

- **`TeamID`** — a soft-isolation field on certificates and approvals, with
  team-based authz (`authorizeCertificateMutationRequest`) and a rule that a
  non-admin principal only sees certs where `TeamID == principal`. An embryonic
  tenant model — but only on certs, not CAs/templates.
- **`AuthPrincipal{ID, Role, Scopes}`** — **no tenant dimension**. Tenancy needs
  a tenant on the principal.
- **CAs and templates are global** — no tenant/owner column. The central gap.
- RBAC roles (`pki-admin`, `pki-operator`, `pki-auditor`) — extend with a
  super-admin / tenant-admin distinction.

## 4. Design decisions (the load-bearing ones)

### Tenant as a first-class dimension (not a reuse of TeamID)

Introduce a distinct **`tenant_id`** as the isolation boundary. `TeamID` stays
as an *intra-tenant* grouping (a tenant can have teams). Reusing TeamID as the
tenant would conflate two concerns and complicate migration. (Open Q1.)

### Flat tenants, not hierarchical folders (for v2.2)

The plan says "policy folders." Hierarchical folders are powerful but complex
(inheritance, nested RBAC). Ship **flat tenants** in v2.2; hierarchical policy
folders are a later enhancement. (Open Q2.)

### Tenant on the principal

`AuthPrincipal` gains `Tenant string` and `SuperAdmin bool`. Sources: a `tenant`
JWT/OIDC claim, a `tenant` field on API-key records, and bootstrap = super-admin.
Every request resolves to (principal, tenant, super-admin?). (Open Q3.)

### Resource tenancy + default backfill

Add `tenant_id` to CAs, templates, certificates, approvals, pending-actions,
schedules, waves. **Existing rows backfill to a `default` tenant** so upgrades
don't break. (Open Q4.)

### Enforcement: filter at the store, deny by default

Every store read takes the caller's tenant and filters by it; every write stamps
it. Super-admin may pass an explicit tenant or `*`. The handler resolves tenant
once and passes it down — no handler trusts a client-supplied tenant_id except
super-admin. Deny-by-default: a missing tenant context = empty result, not all.

## 5. Waves

| Wave | Content | Notes |
|------|---------|-------|
| **W1** | Tenant model + principal tenancy: `tenants` table + registry, `AuthPrincipal.Tenant`/`SuperAdmin`, tenant resolution in auth, `tenant_id` on **CAs + templates** (migration + default backfill), tenant-scoped CA/template list + issuance | The boundary + the issuance path |
| **W2** | Tenant-scope the rest: `tenant_id` on certificates / approvals / pending-actions / schedules / waves; filter every list + stamp every write; super-admin bypass; **cross-tenant isolation tests** (a tenant must not read/act on another's resources) | The exhaustive, security-critical pass |
| **W3** | Tenant management UI (super-admin: create/list tenants), a tenant switcher, per-tenant scoping of the dashboard; tenant column where useful | Operability |

Each wave is its own PR with isolation tests; W2 especially must prove the
boundary holds for **every** resource type.

## 6. Risks

- **Cross-tenant leak** (the cardinal risk): mitigate with store-level filtering
  + deny-by-default + explicit negative tests (tenant A cannot see/modify tenant
  B's CA/cert/approval/etc).
- **Migration**: existing single-tenant data must keep working — backfill to
  `default`, and a deployment with no tenants configured behaves as today
  (everyone in `default`).
- **Super-admin footgun**: cross-tenant actions must be explicit (never the
  accidental default) and audited with the target tenant.
- **Blast radius**: every store/handler changes — land W1/W2 behind tests and
  review; consider a feature flag (`MULTI_TENANCY=on`) so it's opt-in until
  proven, defaulting to single-tenant behavior.

## 7. Decisions (locked 2026-06-18)

1. **New `tenant_id` dimension**, teams nested inside (TeamID stays intra-tenant).
2. **Flat tenants** for v2.2; hierarchical policy folders later.
3. **Tenant on the principal** via a `tenant` JWT/OIDC claim + API-key tenant
   field; bootstrap = super-admin.
4. **`MULTI_TENANCY` feature flag, default OFF.** When off: single-tenant —
   every principal resolves to tenant `default` + super-admin, so no filtering
   changes behavior. When on: enforcement active.

### Implementation note — CA scoping without touching `internal/ca`

CAs live in the `ca` package with their own store/key material. Rather than
modify that package, W1 maps tenancy in a bootstrap-side `ca_tenants` table
(ca_id → tenant_id) and filters the CA list/issuance there. Unmapped CAs ⇒
`default` tenant.

### Adjusted waves

- **W1**: `tenants` table + store + super-admin tenant CRUD; `AuthPrincipal`
  tenancy + flag-gated resolution; `ca_tenants` mapping + tenant-scoped CA list;
  isolation test (tenant A can't see tenant B's CA when the flag is on).
- **W2**: tenant-scope templates + certificates + approvals + pending-actions +
  schedules + waves (filter every list, stamp every write); exhaustive
  cross-tenant isolation tests.
- **W3**: tenant management UI + tenant switcher + per-tenant dashboard.

## Known limitations (v1)

- **CA-less certificates belong to the default tenant (S-06, 2026-10-18).**
  A certificate's tenant is derived from its issuing CA (`ca_tenants`). A
  certificate with no hub CA (`ca_id` empty: imported, discovered, synced) has
  no derivable tenant: `certificates` carries no tenant column and the
  importing principal's tenant is not recorded, and a team id is not mapped to
  a tenant. Under `MULTI_TENANCY=on` such a certificate therefore resolves to
  `default`. It is visible to, and revocable by, default-tenant certificate
  admins, and is not visible to the non-default tenant that imported it.
  Revoking one is inventory-only (see `revocation_scope`), so there is no
  CRL/OCSP effect. Operators who need a tenant to own imported inventory
  should run it as `default` or keep the estate single-tenant until a tenant
  column on `certificates` ships (same follow-up as the D-203 agent/NHI/SPIFFE
  tables). Access was deliberately not widened to compensate.
