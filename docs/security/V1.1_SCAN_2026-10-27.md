## Checked and found clean

- **Plugin signing**: a wrong signature or unknown key is refused; the sha256 pin is checked over the
  exact bytes compiled (no verify/compile TOCTOU apart from A-02); the catalogue must be signed,
  https only, same-host redirects (max 3); no production skip-signature flag.
- **Plugin sandbox**: no WASI FS/env/args, no sockets; `http.do` is https-only, host+port granted,
  and on the egress client whose dial-time check blocks metadata, link-local, NAT64 and loopback
  (DNS-rebinding safe); a plugin cannot set the Host header; `pathAllowed` rejects traversal;
  SSH and WinRM argv are quoted.
- **Credential sources**: admin-only and tenant-gated (fail closed); `/test` returns field names
  only; Vault errors never echo the response body; the opt-in cache is capped at 300 s and zeroized.
- **Windows installs**: every PowerShell/cmd argument (subject, store, SQL instance, Exchange
  services, IIS fields) is quoted or validated; PFX passwords come from crypto/rand; service
  accounts get read-only key access; SQL/RDP/IIS/Exchange rollback never leaves a weaker cert.
- **Trust push**: bundles need dual control plus super-admin; agent opt-in is off by default; the
  sudoers rule allows one exact command; the parser takes CA certificates only, with size/count
  caps; removal only touches roots Kryptkeeper added.
- **Agent↔hub auth**: DB-store tokens are 256-bit, hashed, constant-time compared; every agent
  route checks agent id and token together (no cross-agent IDOR); admin agent views are
  super-admin-gated; `agentclient` never sets `InsecureSkipVerify`.
- **Intune SCEP**: Intune validates the whole CSR and transaction id before anything is signed;
  outages fail closed; no token or secret reaches logs.
- **ACME device-attest**: root pinning, nonce binding, CSR-key binding, exact permanent-identifier
  matching and the tenant-bound inventory hold; no way found to get a cert for another device.
- **External CAs / cloud inventory**: connector and Intune clients are on the egress-guarded client,
  TLS verification never turned off (the one bypass is the fixed-address GCP metadata client);
  upstream responses are checked against the request and configured trust anchors.
- **ML-DSA PKCS#8**: length-guarded, no panics found by reading; key material zeroized in delivery.
- **Routes**: all 22 OpenAPI paths added since v1.0.0 plus new registrations hold their role and
  tenant checks apart from C-10/C-14; none breaks D-202 or D-203.
- **Integrations (lane D)**: ITSM connections, events and tests are tenant-stamped and filtered;
  `credential_ref` is checked for tenant visibility; ITSM, notify and ticket plugins use the
  egress-guarded client; test results return a generic reason, never upstream bodies.

#### Checked and clean (with evidence)

- **Signature verification.** It covers the exact manifest bytes (`Classify`, delivery_plugin_signing.go:130-148): ECDSA P-256 `VerifyASN1` over sha256(manifest), the same digest cosign sign-blob signs. A bundle's `messageDigest`, when present, must equal that digest (:173-177). A wrong signature, or one from an unknown key, is refused, never downgraded (:148). A signed install must send the raw bytes as `manifest_base64` (handlers_delivery_plugins.go:106-110). There is no Rekor/Fulcio and no network dependency. Keys must be P-256 (:114-116).
- **Manifest-to-module binding and TOCTOU.** The manifest pins `artifact.sha256`. The hash is checked in `Install` (:156-158) and again in `Runtime.Load` (runtime.go:112-115) over the same in-memory bytes that are then compiled (:122). `Enabled` re-reads the stored bytes and re-hashes them through `Load` before compiling (delivery_plugins.go:478-485). There is no gap between verify and compile, except the cache issue in A-02.
- **Catalogue trust.** The catalogue must be signed by a held key; an unsigned catalogue is refused (plugin_catalogue.go:93-101). Its entries are bound to the files by wasm sha, id, version and manifest sha (:196-207), and the bundle is mandatory (:211-213). The client is egress-guarded, HTTPS-only (the `!egressAllowLoopback` test seam is a package var, not an env var), follows same-host redirects only, at most 3 (:69-78). #### Areas checked and found clean

- **Intune SCEP (Q1):** Validate runs before issuance and any error (refusal or outage) denies; only `code=="Success"` passes (intune/client.go:452-465). The whole CSR and SCEP transactionId are sent to validateRequest, so the result is bound to the CSR (subject/SAN/KU via Intune's own mismatch codes). Template enroll gate runs first; unsupported SAN types (UPN/email), unknown EKUs and CA key usages are refused (intune_flow.go:181-230). Renewal is not offered on labels (server.go:268-275, 362-367). Outer PKCS#7 and CSR signatures verified (server.go unwrapRequest). Label admin API is admin + super-admin-global + credential tenant/type checked (handlers_scep_labels.go:54-70,173-181) and write-gate permAdmin. Token handling: client secret / PS256 assertion never logged; token errors repeat only the OAuth error code; tokens cached per tenant|client|ref; Graph-discovered service URL must be https; all calls on egress client with RequireHTTPS (scep_intune.go:59-66).
- **ACME device-attest (Q2):** Roots are operator-supplied pools; Apple freshness = SHA-256(token) compared in constant time; TPM extraData = H(keyAuthorization) so it is account-bound; certInfo magic/type, AIK signature, name-of-pubArea, RSA >= 2048 / ECC on-curve checked; AIK cert profile (v3, empty subject, AIK EKU, not CA, TCG manufacturer, permanent identifier) enforced. Identifier compare is octet-exact including assigner; finalize requires CSR key == attested key (thumbprint), CSR self-signature, key strength, no DNS/IP/URI/email SANs, at most the ordered permanent identifier, not the account key; cert identity comes from the order, not the CSR; template flag + inventory re-checked at finalize; inventory check is tenant-bound to the CA's tenant and fails closed on error. CBOR decoder bounded (depth, sizes, no tags/indefinite). No path found to obtain a cert for another device's identifier without a valid attestation naming it.
- **PQC wave (Q3):** successor key id is generated per member; delivery target must pass `targetMayReceiveCert` (CA visible to target tenant); unsupported install modes refuse; exported key DER/PEM zeroized; export audited; execution is approval-gated (write gate action.approve). Template algorithm policy is not enforced on RenewCertificate (documented pre-existing, pqc_wave_execute.go comments).

Connector/CA/credential tenant re-checked at issue time; create is admin + dual-control gated.
