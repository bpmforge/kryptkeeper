# UI review — 2026-07-31

Observed by driving the **production bundle against the real backend** with a
real PKI on screen (Acme Root CA → Acme TLS Issuing CA → 3 issued certificates),
not the dev server. That distinction matters: `npm run dev` serves MSW fixtures,
so anything reviewed there is a mock.

**Scope, honestly stated:** five screens were examined closely — Dashboard,
Certificates, Certificate Authorities, CA Health, Settings — plus the issuance
wizard and login. The remaining 26 destinations were reached and confirmed to
render, but not reviewed pixel by pixel. Findings below are therefore a real
sample, not a complete audit.

## What is working well

The visual system is coherent and clearly deliberate:

- **Consistent page scaffold** — eyebrow label, H1, one-line purpose, then
  content. Someone landing cold knows what a screen is for.
- **Split inspect layouts** (inventory left, detail right on Certificates and
  CAs) put the record and its detail on one screen without a modal.
- **Empty states carry instructions, not apologies.** Settings says *"Set
  `SIEM_WEBHOOK_URL` or `SIEM_SYSLOG_ADDR` in the server environment"* with the
  variables in inline code. That is the right answer to "why is this empty".
- **KPI rows** on the report pages read at a glance, with semantic colour
  (green active, red expired, amber warning) applied consistently.
- **Real density discipline** — the certificate detail panel fits fingerprint,
  issuer, validity window, serial, key algorithm, team and grade without feeling
  cramped.

## Findings

### 1. An "active" CA is simultaneously "Expired" — CA Health

`ci-seed-root-ca` renders a green **active** status badge and a red **Expired**
in the same row, with Expires `—` and Algorithm `–`. Two cells of the same row
contradict each other, and the eye lands on whichever it sees first.

Either status should derive from expiry, or an expired-but-active CA needs its
own explicit state so the row reads as one fact rather than two competing ones.

### 2. Strength is graded on an unknown algorithm — CA Health

The same row shows Algorithm `–` and Strength **Acceptable**. A grade asserted
over a value the system does not have reads as a measurement when it is a
default. Absent input should render as absent, not as a passing grade.

### 3. The Reset button is sized like a primary action — CAs

In the CA filter bar, `Reset` occupies a full third of the row (~345px) because
it inherits the grid column its dropdown neighbours use. It out-weighs the
filters it resets and competes with the genuine primary action (`New CA`) at
the top right. Size it to its content.

### 4. Header pattern is inconsistent across screens

- Certificates: eyebrow `INVENTORY` + H1, no icon
- CAs: eyebrow `TRUST` + H1, no icon
- Issue certificate: eyebrow `ISSUANCE` + H1, no icon
- CA Health: **icon + H1, no eyebrow**
- Settings: **H1 only — no icon, no eyebrow**

Four screens, three different header shapes. Whatever the intended rule, at
least one of these is wrong; Settings in particular loses the sense of place the
eyebrow gives every other page.

### 5. Disabled actions are hard to distinguish — Settings

`Send test event` and `Send now` are disabled (no SIEM target, no SMTP) but sit
at nearly the same weight as their enabled siblings `Refresh` and `Add
schedule`. On a dark surface the contrast delta is small enough that the state
is easy to miss, and a user clicks and gets nothing. Disabled controls need a
clearly lower-contrast treatment, and ideally a title explaining the
precondition — the page already knows it ("requires SMTP").

### 6. `display_name` is discarded on CA create

Creating a CA with `display_name: "Acme Root CA"` stores and renders
`acme-root` — the slug. Every CA surface (list, detail, CA Health, Dashboard)
therefore shows machine names where a human name was supplied. Backend
behaviour, surfaced by the UI; likely a create-path field drop.

### 7. ~~Three icon-only buttons expose no accessible name — CAs~~ STRUCK

**This finding does not reproduce and is withdrawn.** A full button inventory of
`/cas` returns 12 controls, every one carrying text, none containing an `svg`.
The claim came from an accessibility-tree snapshot taken in a different session
state.

A real defect sits in the same place: the three CA rows are `<button>` elements
whose text content concatenates without separators, so the accessible name is
`"acme-rootroot · softwareactive"`. See I-4 in
[ANALYST_REPORT_2026-07-31.md](ANALYST_REPORT_2026-07-31.md).

## Cross-cutting: the session expiry problem

Filed separately as **S-38**, repeated here because it is what a user actually
sees. The access token lives 15 minutes and nothing refreshes it, so screens
degrade into their unauthenticated fallbacks *while still looking like data*:
the user chip becomes a dash, 12 of 31 nav destinations disappear, the issuance
wizard renders "Read-only access", and the certificate inventory says **"No
certificates issued yet"** while the API returns three for that same principal.

Every one of those is a truthful-looking screen showing a false thing. It is the
single highest-impact UI issue found.

## Reproducing this environment

```bash
# API with the real CA engine
APP_CERTIFICATE_PROVIDER=ca KRYPTKEEPER_KEYSTORE_PASSPHRASE=... \
APP_AUTH_LOGIN_ENABLED=true APP_AUTH_LOGIN_ROLE=pki-admin ... ./dist/kryptkeeper

# Production UI bundle + /api proxy — NOT `npm run dev`, which serves mocks
npm --prefix ui run build && node serve-real.mjs
```

`npm run dev` will show 247 certificates and 84 endpoints that do not exist.
Review against the production bundle or you are reviewing `src/mocks/fixtures.ts`.
