# Kryptkeeper v1.3 — Renewal Autopilot (Scope)

**Date:** 2026-06-16
**Plan reference:** `docs/archive/GO_FORWARD_PLAN.md` §4 Moat 1
**Status:** SHIPPED — v1.3.0 (tagged; see CHANGELOG.md). This doc is the original scoping record; per-item statuses below are historical. _(Re-statused 2026-07-15, design review G-7.)_

## 1. The one-line promise

> Point the agent at a server. Every cert on it renews, installs, reloads, and
> verifies — forever. The dashboard shows automation coverage as an SLO.

This is the core value moat: nobody in OSS closes the discover→issue→**install**→
verify loop. v1.3 closes it.

## 2. Current state (code-verified 2026-06-16)

What already exists:

- **Agent lifecycle**: `internal/agentclient` — register
  (`POST /api/v1/agent/register`), heartbeat, inventory push
  (`POST /api/v1/agent/inventory`), task poll (`GET /api/v1/agent/tasks`).
- **Renewal**: `AcmeRenewer.Renew(domain, webRoot)` runs ACME http-01 via a
  challenge file under `webRoot/.well-known/acme-challenge/`, returns
  `RenewResult{CertPEM, KeyPEM}`.
- **Install-target discovery, partial**: `agentdiscovery/configparser.go`
  already extracts `ssl_certificate` (nginx) and `SSLCertificateFile` (Apache)
  paths from config files. **The path where the cert must be written is already
  known.**
- **Hub-side renewal scheduler** (wired in v1.2) triggers renewal candidates.
- **ARI staggering** (v1.1) prevents thundering herds.

### The gap (precisely)

In `cmd/kryptkeeper-agent/main.go`, `renewAsync` calls `Renew(...)` and then:

```go
log.Printf("renewed %s: cert %d bytes", task.Subject, len(result.CertPEM))
```

That's it. The renewed cert is **logged and discarded**. It is never:
1. **Installed** — written to the path the workload reads
2. **Reloaded** — the web server is never signaled to pick up the new cert
3. **Verified** — nobody confirms the new fingerprint is actually being served
4. **Reported** — the Hub never learns the renewal landed; lifecycle ends at "issued"

The config parser also only captures the **cert** path, not the **key** path
(`ssl_certificate_key` / `SSLCertificateKeyFile`), the server **type**, or the
**reload** method — all needed to install safely.

## 3. Deliverables

### A. Agent — install + reload + verify (the core)

- **A1. Installer** (`internal/agentinstall`): atomic write of cert+key to the
  discovered paths — write to temp, fsync, back up the existing file, rename
  into place; roll back on failure. nginx first.
- **A2. Reloader**: validate-then-reload per server type. nginx: `nginx -t`
  **before** reload (abort if config invalid), then `nginx -s reload` /
  `systemctl reload nginx`. Reload command configurable; never a hard restart.
- **A3. Verify-after-install**: TLS dial to the endpoint
  (`host:443` from `server_name`/listen), read the served leaf, assert its
  SHA-256 == the newly issued fingerprint. Renewal is "done" only when verified.
- **A4. Rollback**: if `nginx -t` fails or verify fails, restore the backed-up
  cert/key and reload again; report failure.

### B. Discovery — capture the install contract

- **B1.** Extend `configparser.go` to also capture `ssl_certificate_key` /
  `SSLCertificateKeyFile`, the server type (nginx/apache), and the
  `server_name` + listen port — emit an **Endpoint** record (cert path, key
  path, server type, reload method, verify host:port).
- **B2.** Agent reports endpoints in its inventory so the Hub knows what's
  installable.

### C. Hub — task contract + result lifecycle + SLO

- **C1.** Extend `RenewalTask` with install hints (target cert/key paths,
  reload method, verify host:port) so the agent knows where/how.
- **C2. New endpoint** `POST /api/v1/agent/renewal-result`: agent reports
  install/verify outcome (success | install_failed | verify_failed | rolled_back)
  + served fingerprint; Hub updates the cert renewal lifecycle and writes audit.
- **C3. Renewal SLO aggregation**: % of inventory on autopilot, mean time to
  renew (issued→verified), failed-renewal queue. Reuses the v1.2 daily-snapshot
  pattern for trending; new `GET /api/v1/reports/renewal-slo`.

### D. Dashboard — the SLO surface

- **D1.** New **Automation page** (moves the v1.2 scheduler-status panel here):
  autopilot coverage %, MTTR, and a **failed-renewal queue** with a manual
  retry action.
- **D2.** Per-cert renewal lifecycle badge (issued → installed → verified) on
  the certificate detail panel.

## 4. Suggested waves

| Wave | Content | Why first |
|------|---------|-----------|
| W0 | B1/B2 endpoint discovery + C1 task contract | Everything downstream needs the install target |
| W1 | A1 installer + A2 reloader (nginx, with `nginx -t` gate + rollback) | The core capability |
| W2 | A3 verify-after-install + A4 rollback-on-verify-fail + C2 result endpoint | Closes the loop honestly |
| W3 | C3 SLO aggregation + D1 dashboard panel + D2 lifecycle badge | Makes it visible/sellable |
| W4 | Apache support (reuse A1–A4 with apachectl) | Second-largest fleet |
| (later) | IIS (Windows agent), HAProxy | Smaller fleets |

## 5. Risks & decisions

- **Privilege** (DECIDED — sudoers allowlist): agent runs unprivileged; a narrow
  sudoers drop-in permits only `nginx -t`, the reload command, and writes to the
  configured cert dir. The systemd installer lays down the drop-in. No root agent.
- **Safety first**: always `nginx -t` before reload; always back up before
  overwrite; always verify after; auto-rollback on any failure. A bad cert
  install must never take a site down.
- **Dry-run mode**: agent flag to compute+report what it *would* do without
  writing — needed for first-touch trust.
- **Verify reachability**: the agent must be able to reach the endpoint it just
  installed to (usually localhost:443) — document the assumption.
- **Key handling**: renewed private key is written to disk by the agent; ensure
  `0600`/correct ownership and never logged.

## 6. Out of scope for v1.3

- IIS / HAProxy / F5 (later waves or deliberately-not-doing per go-forward §6)
- Non-web-server cert consumers (databases, message brokers) — future
- SSH-key inventory/rotation (still awaiting a discovery source; see
  `docs/v1.2_VISIBILITY_SPRINT.md`)

## 7. Decisions (locked 2026-06-16)

1. **Privilege model: sudoers allowlist** (least privilege). Agent runs
   unprivileged; install ships a narrow sudoers entry permitting only
   `nginx -t`, the reload command, and writes to the configured cert directory.
   No root agent. The agent installer (systemd unit) must lay down this sudoers
   drop-in at setup time.
4. **Dashboard home: a dedicated Automation page.** Move the v1.2 renewal-
   scheduler status panel there too, and add the autopilot SLO + failed-renewal
   queue. Settings keeps integration config (SIEM); Automation owns scheduler +
   autopilot + SLO.

### Still open (defaults chosen, override anytime)

2. **Reload strategy**: auto-detect — prefer `systemctl reload <svc>` when the
   service is systemd-managed, else fall back to the binary's `-s reload`;
   configurable override per host. (default)
3. **Failed-install policy**: auto-rollback only — restore the backed-up
   cert/key and reload; report `rolled_back` to the Hub. Do not auto-revert the
   Hub's issuance record (the new cert is valid; only its installation failed).
   (default)
